# Sportura: ответственность команды до следующей проверки staging

Дата: 19 октября 2026. Целевая ветка — `dev`, staging — <https://staging.sportura.kz>.
Владелец файла исправляет его сам. Проверяющий читает код и сообщает замечания;
он не коммитит исправления в чужую часть. Искандер совмещает свою работу
с координацией и принимает общие изменения; отдельного координатора Codex нет.

## Работа и запас лимита

Надир (Claude Max 20x) получает примерно 65% объёма работы, Искандер
(ChatGPT Plus) — 35%, включая около 10% на координацию. Это доли работы,
а не гарантированные
проценты лимитов: текущий остаток каждой подписки неизвестен. Перед началом
проверить доступный остаток и время сброса, оставить минимум 25% доступного
лимита на проверку и исправления. Выполнять один законченный пакет, избегать
параллельных полных аудитов и повторных сборок без новых изменений.

## Изоляция и интеграция

У каждого отдельный worktree и ветка от одного согласованного SHA `origin/dev`:

```sh
git fetch origin dev
git rev-parse origin/dev
git worktree add ../Sportura-nadir -b codex/nadir-event-readiness origin/dev
git worktree add ../Sportura-iskander -b codex/iskander-feed-polish origin/dev
```

Команды выполняет координатор один раз; существующие ветки/worktree не
пересоздавать. Оба автора сохраняют исходный SHA в описании PR. Каждый пушит
свою ветку и открывает PR с base `dev`. Прямой push в `dev` выполняется только
координатором, если он выбрал интеграцию без PR. Не пушить в `main`, не делать
force push и не переписывать опубликованную историю. После первого merge
второй автор делает `git fetch origin dev` и `git merge origin/dev` в своей
ветке, затем повторяет затронутые проверки. Общие контракты остаются прежними.

Перед коммитом и повторно перед PR из своего worktree:

```sh
git fetch origin dev
node scripts/check-task-scope.mjs nadir origin/dev
# В worktree Искандера:
node scripts/check-task-scope.mjs iskander origin/dev
# При интеграции Искандером разрешённых общих файлов и ленты:
node scripts/check-task-scope.mjs iskander-coordinator origin/dev
```

`origin/dev` можно опустить. Проверка учитывает `git diff <base>...HEAD`,
staged, unstaged и новые неигнорируемые файлы; при удалении/переименовании
проверяются исходный и новый пути. Проверка общая для всего worktree: чужие
локальные изменения тоже вызовут отказ. Это добровольная проверка границ,
а не права доступа репозитория или защита веток. Она не подключена к CI.
Изменение контракта/общего файла сначала передать координатору с причиной
и минимальным необходимым изменением; самостоятельно границы не расширять.

## Приёмка, дизайн и взаимная проверка

Для каждого пакета: `npx tsc --noEmit`, ESLint затронутых файлов,
`git diff --check`, целевые регрессии. Полный `npm test` и production-сборка —
перед готовностью своего PR; повторять после изменений, влияющих на результат.
После совместного merge координатор проверяет объединённый `dev` и реальный
статус staging deployment; успешный push сам по себе не подтверждает деплой.

Дизайн обязателен: Надир проверяет host на 390 и 1280 px, Искандер — ленту
на 360/390/768/1280 px. Для обоих: RU/KK, светлая/тёмная темы, клавиатура,
видимый фокус, закрытие диалогов и возврат фокуса, цели касания минимум 44 px,
отсутствие обрезанного текста и горизонтального скролла. Скриншоты до/после
должны показывать ширину, тему, язык и состояние; в отчёте указать проверенный
SHA, маршруты, сценарии и оставшиеся проблемы. Проверить также страницы,
которые используют изменённые общие визуальные компоненты.

Взаимная проверка после готовности обоих PR, только чтение (ссылки заменить
реальными):

```sh
gh pr view <PR_NUMBER> --json baseRefName,headRefName,headRefOid,url
gh pr diff <PR_NUMBER> --name-only
gh pr diff <PR_NUMBER>
gh pr checks <PR_NUMBER>
```

Искандер проверяет путь организатора и отчёт Надира; Надир проверяет
функциональность ленты и отчёт Искандера. Замечания возвращаются владельцу,
включая точный сценарий воспроизведения и путь. Чужой код не редактировать,
PR не переводить в готовность до устранения критических замечаний.
